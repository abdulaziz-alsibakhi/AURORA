# AURORA Data Dictionary

## Purpose

This is the canonical registry for the semantics of important AURORA data.

It answers:

**What exactly is this datum?**

It does not by itself answer whether a value is good, bad, unusual, concerning, or
acceptable. Those interpretation rules belong under `../validation/`.

## Required fields

Before an important variable is relied upon by a controlled experiment, its entry
should identify as applicable:

| Field | Required interpretation |
|---|---|
| Canonical name | stable project name |
| Source name | source/simulator/dataset field or vector |
| Meaning | physical/technical definition |
| Kind | raw, measured, simulated, predicted, derived, normalized, diagnostic |
| Scope | field, well, grid/cell, controller, safety layer, experiment |
| Entity | relevant well/cell/model/etc. |
| Units | explicit units |
| Sign convention | explicit direction/sign semantics |
| Time basis | instant, interval, report step, control step, cumulative |
| Spatial basis | point/well/grid/field/etc. |
| Provenance | exact source and transformation |
| Missing semantics | what absent/NaN/null means |
| Validity checks | structural/domain checks |
| Controller-visible? | yes/no/conditional |
| Safety-model input? | yes/no/conditional |
| Telemetry role | if logged |
| Interpretation reference | applicable interpretation contract/rule |
| Status | provisional or frozen |

## Data classes

### Source/raw data

Values read directly from an external dataset, simulator output, or controlled input.

Raw does not mean correct.

### Simulated physical quantities

Quantities generated by OPM under a defined numerical experiment.

These are simulator outputs, not field measurements.

### Real-field data

Values originating from Volve or another documented real-world source.

Real-field origin does not automatically make a value appropriate for the Egg
experiment.

### Model predictions

Outputs from CRM/ROM or another predictive model.

A prediction must remain distinguishable from the reference quantity it attempts to
predict.

### Derived quantities

Values calculated from one or more other values.

Their lineage and formula must be reconstructable.

### ML representations

Normalized, scaled, windowed, encoded, stacked, or otherwise transformed values used
by a learned model.

Their physical source and inverse interpretation should remain traceable where
practical.

### Decision quantities

Proposed actions, projected/applied actions, constraint margins, intervention
magnitudes, feasibility indicators, or related control outputs.

## Transformation lineage

For every important derived/model quantity AURORA should be able to reconstruct:

    source
      -> extraction
      -> validation/cleaning
      -> transformation
      -> model input
      -> model output
      -> derived metric
      -> interpretation
      -> decision/intervention
      -> experiment result
      -> report claim

## Pressure example

The following are separate semantic objects:

1. OPM-produced physical pressure quantity;
2. normalized pressure supplied to ML;
3. CRM-predicted pressure;
4. OPM-minus-CRM pressure residual;
5. uncertainty/calibration quantity derived from residuals;
6. pressure-related QP expression;
7. realized constraint margin;
8. safety-intervention diagnostic.

They must never share an ambiguous generic field name such as `pressure` in a context
where the distinction matters.

## Freeze rule

A variable becomes **frozen** only when:

- source semantics are verified;
- units/sign/time basis are known;
- transformations are defined;
- missing/stale handling is defined;
- subsystem visibility is defined;
- validation checks exist;
- interpretation rules are linked; and
- relevant interface/architecture decisions are approved.

Until then, mark it provisional/unfrozen rather than guessing.
